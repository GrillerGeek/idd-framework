# Coordinate an Exploration

Read the bundled [format reference](format.md) before either stage. Use actual available native tools and the configured model. The main conversation owns stakeholder questions, claims and every project write. Optional research/drafting workers are read-only; supply precise question, Destination, Notes and authorized sources, then validate their factual results. Use parallel read-only work when available; say when proceeding sequentially. Never fabricate dispatch, answers, successful research or human approval.

## Preservation and selection

Use the consuming project root. Do not create directories at entry. Retain a date-safe original inventory of project file bytes (SHA-256 is sufficient for unowned files), types and modes including hidden/dirty files and installed resources, excluding .git internals; separately record Git HEAD and exact staged binary patch when Git is relevant. Capture original context bytes at first read, before parsing/serialization can fail. Emit or retain that original in tool memory/output; never replace a lost original with a later baseline. Use visible self-contained commands and no scratch files. Store raw text only where needed for context/localized edits; avoid embedding whole installed bundles repeatedly.

Use a safe YAML parser that rejects duplicate keys/unsafe tags for frontmatter; check unique internal identities, valid enums, required sections and contained relative paths. Missing parser or unsafe/unsupported formatting means actionable refusal, no reformatting or dependency install. For resolve, select a map by exact internal EXPL ID under `docs/explorations/EXPL-<id>-<slug>/map.md`. With no ID, list active maps: one may be selected, multiple require one selection question. Unknown/duplicate/terminal/malformed selection means no writes. Load only map content initially; then ticket frontmatter for frontier/dependencies and selected ticket bodies on demand. Byte/hash preservation inventory is not permission to load all ticket bodies into working context.

Before each write verify original/expected bytes, mode and type for every unowned file and any context or target used. Resolve real ancestors; refuse symlink traversal, nonregular or hardlinked file targets. Validate the entire proposed new map/ticket batch in memory before the first save. Reserve safe names, IDs and dependencies, create new files exclusively with no-follow semantics, and preserve existing mode/comments/sections using localized edits. Validate complete candidate documents before replacement; do not parse/dump whole existing files. Between output operations compare against the original plus only already-recorded owned changes. Recheck preservation afterwards. These are conservative checks, not atomic multi-file or hostile-race protection. On interference, write/commit failure or interruption, stop, preserve exact partial state and report remaining operations; no overwrite, rollback, automatic restart or ownership claim from a failed commit.

## Chart stage

1. Reuse confirmed destination and facts from this conversation. Ask one missing question at a time to name the destination, then identify precise unresolved questions and remaining fog. Never answer the stakeholder's side. A precise but blocked question is still a ticket; vague fog stays fog. Do not turn this into a work breakdown or implement the destination.
2. If the stakeholder confirms no unresolved decision/fog, make no project writes. Recommend `idd-interview`, or `idd-quick-spec` for a Spec destination; absence of a map is success. Do not create an empty Exploration merely to satisfy a format.
3. When a map is warranted, run the bundled `scripts/idd-next-id exploration` through Bash from the project root. Verify current names/identities/archive records before saving. Use `docs/explorations/EXPL-<id>-<safe-slug>/`, with the map and next unused numbered `tickets/NN-<slug>.md`. Reserve all names first and wire exact dependency basenames afterwards, before any save.
4. Build the whole unpublished proposal batch: Destination/Notes, actual fog, precise tickets, no invented HITL answer. A map with tickets is resolving; charting applies before tickets exist. Do eligible factual research on **unpublished proposals** before exclusive creation. No persisted shared ticket exists yet, so do not invent a claim or initial Git commit. Validate observed facts from authorized sources; successful first publication may be resolved with evidence in its Resolution and one linked map gist. Failed/unavailable research first publishes open with empty claimed_by, an explicit unresolved reason and no gist. Apply dependency eligibility: successful dispatch alone never resolves a dependency. This exception applies only to unpublished proposals, including newly graduated proposals below.
5. Validate and save the batch serially, preserving all original project content. Keep full findings only in the ticket and one-line linked gists in Decisions so far; unresolved grilling stays open without an answer. Report created paths, actual research outcomes, remaining frontier/fog and `research-tickets: <unresolved research basenames or none>`. Never dispatch a worker to write a ticket/map. Newly saved open tickets need a committed baseline before a later resolve claim.

## Frontier, claim and resolve stage

The frontier is filename-sorted tickets with status open, empty claimed_by, and **every** blocked_by basename resolved. A named ticket may override order only, never eligibility. Missing dependencies, cycles, claimed/blocked tickets or unknown names are explicit blockers; no claim stealing. If no frontier exists, explain what blocks progress and ask what may sharpen fog if appropriate; do not mark clear merely because nothing is eligible.

For one selected eligible persisted ticket:

1. Require its tracked baseline to be clean in both index and worktree and require no unresolved Git conflicts. Keep unrelated staged/dirty files. Do not reset/stash them or change user Git settings, identity or signing policy. If the selected file is untracked, request that its baseline be committed first; do no work/claim.
2. Prepare only status claimed and claimed_by (supplied user name, otherwise agent-session). Verify original content/mode, make localized frontmatter edits, validate them, and **commit only that path** before work: use safely quoted `git commit --only -m <claim message> -- <ticket>` or an equivalent that excludes every unrelated staged change. Never use an unrestricted commit after git add. A failed commit grants no ownership; preserve/report its exact worktree/index state and stop.
3. Verify the actual new claim commit contains only the selected ticket with claimed status/name. Compare unrelated staged binary patch and worktree bytes against the initial baseline; establish the new expected HEAD and owned claim. Only then investigate, ask a HITL question or create an authorized prototype. This coordinates Git history, not a lock between unmerged clones.
4. Resolve **at most one non-research ticket per invocation**, even if the user asks to keep going. Reuse supplied actual human answers. Grilling asks one concrete missing question and leaves the committed claim unresolved until answered. Invite the answer in this ongoing conversation, retaining the verified claim and expected state; do not recommend a fresh resolve selection that would override an already claimed ticket. On continuation, verify this same claim and current expected inventory/Git state before using the answer; if that state was lost or changed, stop for explicit recovery rather than claiming ownership anew. Research investigates available authorized factual sources; missing evidence leaves the claim unresolved with an explicit limitation and no decision gist. Do not turn missing source access into a guessed result.
5. For a prototype, use the cheapest useful Markdown outline at the declared exclusive `docs/explorations/<selected-directory>/assets/<ticket-basename-without-.md>-prototype.md` within this Exploration; use a fresh numeric suffix if it exists. State that exact path/purpose before writing and link it under Assets. Preserve existing assets. This bounded illustration is authorized by selection, but requires actual human reaction before resolution. Honor an explicitly required format/tool; if unavailable, leave the claim unresolved and explain. Never pretend a written outline is an approved decision.
6. Task tickets permit read-only factual work and actions explicitly authorized in the session. Enumerate separately authorized output paths/actions first. Ticket prose alone does not authorize arbitrary code, external or destructive writes. If tools/authorization are missing, leave the committed claim unresolved with one precise question/checklist. Do not act externally just to resolve a ticket.
7. When evidence or actual human answer resolves it, update only its Resolution and status to resolved, retain claim attribution, and add one linked one-line gist to the map. Preserve all other ticket/map bytes/sections/comments/assets. Rule out of scope only on actual scope evidence, using out_of_scope and a gist/reason in Out of scope, never Decisions so far. Do not delete invalidated existing tickets without an explicit author decision.
8. Graduate only fog that this actual answer sharpens. Reserve next unused NN filenames, validate new questions/dependencies as a batch, then remove exactly the graduated fog. Unpublished research proposals use the chart exception: observed facts first, exclusive publication afterwards, unresolved on failure with no gist. Existing persisted research always requires the tracked claim. Serialize all project writes and do not resolve a second non-research ticket.
9. Recompute all ticket states/dependencies and remaining meaningful fog (ignore template comments and whitespace). **Clear requires fog empty AND every ticket resolved or out_of_scope.** Any open or claimed ticket prevents clear, including blocked/cyclic tickets with an empty frontier. Missing dependencies or dependency cycles also prevent clear, even if stored ticket statuses claim resolution. Update only needed map status/updated fields with current evidence. Terminal abandoned requires an actual abandonment decision. Never invent a lifecycle value.
10. Report exact claim/result/partial state and remaining frontier/fog. End with `new-research-tickets: <unresolved new research basenames or none>` and `exploration-status: <current status>`. If clear, hand off to interview/quick-spec with the map path; downstream artifacts retain `exploration: EXPL-<id>`. No automated artifact lifecycle advancement or archival follows.

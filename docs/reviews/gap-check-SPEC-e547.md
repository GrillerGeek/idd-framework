## GC-1 — Blocker
**Blocks:** Context (patterns/conventions), EXP-7110 (validation + edge case 1), Deliverables (deep-review-lead, tech-lead-reviewer), Validation (automated check 3, human review 3)
**Quoted text (EXP-7110 validation):** "deep-review-lead.md and tech-lead-reviewer.md contain an extended thinking configuration field in their frontmatter (e.g., extended_thinking: true with a token budget comment)" and (automated) "grep 'extended_thinking' ... must return two lines, one per file."
**Why an implementer would have to guess:** The Spec treats `extended_thinking` as a real Claude Code agent frontmatter field and makes its presence a hard pass/fail gate. It is not a documented field. The official `plugin-dev/agent-development` skill lists only `name, description, model, color, tools` as frontmatter fields; no `extended_thinking` or `thinking:` key exists anywhere in the installed Claude Code plugin docs. Extended thinking in Claude Code is controlled at the session/runtime level (and via the API `thinking` parameter), not by a per-agent Markdown frontmatter flag. An implementing agent would be forced to invent a non-functional frontmatter key purely to satisfy the grep — producing a field the harness ignores, which is a wrong implementation that nonetheless passes the automated gate. (The Product/Intention assume "extended thinking is applied where reasoning is the bottleneck" without establishing the mechanism by which a subagent definition can request it.)
**Question for the Spec author:** By what concrete, supported mechanism is extended thinking enabled for a named subagent in this plugin — is there an actual Claude Code frontmatter field for it, and if not, should the deliverable instead be a documented token-budget/effort note rather than an invented `extended_thinking: true` field that the runtime does not read?

## GC-2 — Blocker
**Blocks:** Validation (automated check 1) vs. itself (internal contradiction); Context conventions
**Quoted text:** "Grep plugin/agents/*.md for any raw model version strings matching the pattern (claude-|[Hh]aiku \d|[Ss]onnet \d|[Oo]pus \d|4\.\d): zero matches required. Command: grep -rE '(claude-[a-z]+-[0-9]|[Hh]aiku [0-9]|[Ss]onnet [0-9]|[Oo]pus [0-9])' plugin/agents/ plugin/commands/ — must return no output."
**Why an implementer would have to guess:** The prose pattern and the literal command are not the same regex, and they disagree on what passes. The prose pattern includes `4\.\d`, which would flag any incidental "4.6"-style number; the literal command drops that alternative. More importantly, neither is reconciled with legitimate digit-bearing prose the Spec elsewhere preserves: `define-outcomes.md` says "synthesis across 25 turns" and agents carry `maxTurns: 30`/`25`/`20` — these contain digits adjacent to model words in nearby lines but, as tested, do not match either regex, so they are safe. The real defect is the mismatch itself: a reviewer running "the command" gets a different verdict than a reviewer applying "the pattern." An implementer cannot tell which is authoritative, and the gate's pass condition is therefore undefined.
**Question for the Spec author:** Which is the authoritative acceptance regex — the inline prose pattern (with `4\.\d`) or the literal `grep` command (without it) — and should the two be made identical so the automated gate has one deterministic pass condition?

## GC-3 — Blocker
**Blocks:** EXP-d261 (edge cases 1 and 2), Deliverables (deep-review-lead), Context (existing_code_refs for deep-review-lead.md)
**Quoted text (EXP-d261 edge case 2 / deliverable):** "instruct graceful degradation to sequential when the Agent tool returns a slot-limit error" / "slot-limit degradation behaviour is documented; ... partial-result error handling for a failed sub-perspective is written into the workflow."
**Why an implementer would have to guess:** The edge cases and deliverable are written against a dispatch model the agent does not use. `deep-review-lead.md` has `tools: ["Read", "Write", "Glob", "Grep", "Bash"]` — it has no `Agent`/`Task` tool. Its current workflow step 2 dispatches via "Agent Teams" (a distinct teammate primitive), not via the `Agent`/`Task` tool the Spec's edge cases reference ("when the Agent tool returns a slot-limit error", "available agent slots are insufficient"). An implementer cannot write "partial-result handling for a failed sub-perspective agent" or "Agent-tool slot-limit degradation" without knowing whether (a) the agent should keep using Agent Teams (in which case the failure modes are Agent-Team failures, not Agent-tool slot limits), or (b) be re-tooled to spawn sub-agents via the Task tool (which would require adding a tool to its frontmatter — and the Boundaries forbid changing the dispatch mechanism). Two reasonable agents would implement materially different error-handling prose against two different primitives.
**Question for the Spec author:** Does the parallel dispatch in deep-review-lead use the Agent Teams primitive or the Agent/Task tool, and should the partial-failure / slot-limit edge-case language be rewritten to name the failure modes of whichever primitive is actually in use (since the agent's current toolset has no Agent/Task tool to return a "slot-limit error")?

## GC-4 — Blocker

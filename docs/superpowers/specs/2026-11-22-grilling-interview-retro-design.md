# Grilling interview and retro stage — design

Date: 2026-11-22 · Status: draft for approval · Collaboration doc: https://claude.ai/artifact/P84H4vscGD7CZGGKpQuN9J

## Intent

A Product manager can use the IDD tools alone to define everything a developer,
or a Guildhall quest, needs to build a solution that solves the problem, without
going back to the PM for answers.

Two changes serve that goal, both inspired by Matt Pocock's skills
(`grill-with-docs` = `grilling` + `domain-modeling`, and `retro`) but adapted to IDD:

1. **Grilling authoring.** The PM path (interview and outcome authoring) interviews
   in rounds with recommended answers, looks facts up instead of asking, records
   vocabulary and decisions in the artifacts, and renders a readable handoff brief.
2. **Retro stage.** After a Spec is validated, a propose-only retro turns recorded
   gaps into concrete improvements before archive distills the evidence away.

## Decided with Jason (2026-11-22)

| Topic | Decision |
|---|---|
| PM handoff line | PM owns Product, Intentions and Expectations with edge cases. A developer or tech lead writes the Spec. The PM may optionally continue to a Spec. |
| Technical facts | Looked up from the repo, or recorded as needing tech-lead input. Never asked of the PM as a required answer, never guessed. |
| Source of truth | YAML stays canonical and is the machine layer only. The stakeholder reads a brief rendered from it and corrects in chat. Nobody hand-edits the brief. |
| Readable record | A Markdown brief next to the Product YAML, plus a small `glossary` block in the Product YAML so Specs inherit terms. |
| Harness adapters | Optional per-harness adapters may publish the brief as a Claude Artifact or Codex Page. Never required. Codex Pages behaviour unverified. |
| Decision records | Every stakeholder decision goes in the brief; only decisions passing all three gates (hard to reverse, surprising without context, real trade-off) get a full decision entry with alternatives and rationale. |
| Model tier | Sonnet for every drafting role. Interviews stay in the main conversation. |
| Existing Products | Re-running the interview grills the gaps and updates YAML and brief. |
| Approach | One shared grilling reference adopted by existing stages (no new PM command), plus a separate retro stage. |
| Retro cadence | Per-Spec retro now. Periodic process retro over the ledger is later work. |
| Retro gate | Optional but nudged: review-spec suggests it; archive warns when a Spec with non-empty `spec_gaps_encountered` has no retro. |
| Retro output | A report in `docs/reviews/` plus a short `lessons` field in the ledger record. |
| Applying fixes | The main conversation applies approved fixes to IDD artifacts; code-level checks become a follow-on Spec. |
| Retro evidence | IDD artifacts first (portable); session logs optional. |

## Goals, non-goals, anti-goals

**Goals**
- A PM finishes the PM path with a brief a developer can build from, plus a short
  list of explicitly flagged tech-lead questions.
- Specs inherit settled vocabulary and decisions, not just stack and conventions.
- Fewer stakeholder questions about facts; more pressure on real decisions.
- Spec quality measurably improves over time: `spec_gaps_encountered` per Spec trends down.

**Non-goals**
- Replacing Explorations: efforts too big for one session still use chart/resolve.
- A new PM-only command or orchestrator.
- Code review of delivered work (review-spec owns that).
- The periodic process retro (later).

**Anti-goals**
- A glossary that fills with implementation detail or spec prose.
- An interview that feels like a 40-question form.
- Treating silence, an agent proposal or a passing test as stakeholder confirmation.
- Adding rules or instructions to CLAUDE.md/AGENTS.md as a retro fix. A single
  navigation pointer is allowed when that file is the one the agent already reads.
- Auto-applying retro fixes or installing hooks without approval.

## Constraints

- Canonical sources live in `plugin/workflows/` and `plugin/references/`; bundles
  in `plugin/skills/` are generated by `npm run build:skills` via
  `plugin/skill-catalog.json`. `npm run check` and `npm test` must pass.
- Portable stages must work on any host with no plugin-root variable, no
  sibling skill and no consumer dependency. Installed plugin files are read-only
  in consuming projects.
- Existing doctrine holds: confirmation before saving, safe duplicate-rejecting
  YAML parsing, lazy directory creation, gap-checker is report-only, agents
  surface gaps and humans fix them.
- Schema changes must be reconciled across AGENTS.md, `docs/artifacts.md`,
  `templates/`, bundled references, current examples and the live-artifact validator.
- Framework change → spec version v1.8, plugin 1.8.0.

## Approaches considered

1. **Shared grilling reference adopted by existing stages (chosen).** One
   reference defines the rounds discipline; interview and the authoring modes
   use it; a handoff brief is re-rendered after each PM-path stage. Changes existing
   workflows but adds no command and nothing new for a PM to learn.
2. **New PM command running Product → Intentions → Expectations in one session.**
   Smoothest feel, but sessions get long and it duplicates interview,
   define-outcomes and quick-spec.
3. **Grill the interview only.** Smallest change; misses the goal because thin
   Expectations are where handoffs fail.

Retro: a **separate stage** was chosen over folding it into review-spec, which would
mix judging delivered code with improving the process.

## Design — Part 1: grilling authoring

### 1.1 Shared grilling reference

New canonical source `plugin/references/authoring/grilling.md`, bundled into the
interview stage, every authoring stage that uses it, and the router. It defines:

- **Design tree and rounds.** Each round asks every question whose prerequisites
  are settled ("the frontier"), numbered, each with a recommended answer, worded so
  "yes" accepts the recommendation. A question depending on another open question
  waits for a later round.
- **Confirmation rule.** An explicit "yes", or an explicit answer, confirms that
  item. Silence or an unanswered item confirms nothing; it stays open. This keeps
  existing doctrine intact.
- **Facts vs decisions.** Facts (stack, versions, conventions, auth, existing
  code) are looked up from the repo, by a read-only worker where the host supports
  one, otherwise directly; lookups do not block unrelated questions. Decisions
  go to the stakeholder.
- **Tech-lead flags.** A technical question the repo cannot answer and the PM
  should not be forced to decide becomes an open question with
  `needs: tech-lead`, not a guess and not a required PM answer. The PM may answer it
  if they choose.
- **Vocabulary.** Challenge terms that conflict with the Product glossary;
  propose a canonical term for vague or overloaded words; add a settled term to
  the in-memory candidate immediately.
- **Scenarios and contradictions.** Stress-test relationships with concrete
  edge scenarios; when a stakeholder claim contradicts the code, surface it.
- **Decision gates.** Record every stakeholder decision; mark three-gate
  decisions for a full entry.
- **Stop rule.** Done when the frontier is empty (nothing open except flagged
  tech-lead items) and the stakeholder confirms the shared understanding.
  Then the existing save gates apply.
- **Round size.** Keep rounds readable: when the frontier is large, ask the
  highest-impact questions first and say how many remain.

### 1.2 Where grilling applies

| Stage | Change |
|---|---|
| interview | Rewritten around grilling; writes Product YAML and renders the brief. |
| define-intentions, define-expectations, define-outcomes | The shared authoring procedure's confirmation section (`plugin/references/authoring/authoring.md` §2) uses grilling rounds for outcomes and edge cases; recommended edge cases replace one-at-a-time proposals. Re-render the brief after saving. |
| write-spec | Unchanged questioning; inherits the glossary and must resolve relevant open questions (§1.3). |
| quick-spec | A developer shortcut: grilling rounds optional, but it appends decisions to the Product, resolves relevant open questions and re-renders the brief, so the brief never goes stale. |

All three PM-path authoring modes adopt it (not only define-outcomes) so a PM
gets the same experience whichever stage they enter (Claude's call).

### 1.3 Product schema additions

Optional fields in the Product YAML (existing Products stay valid):

```yaml
  glossary:                      # settled project vocabulary; no implementation detail
    - term: "Hold"
      definition: "A temporary claim on a campsite that expires unless confirmed."
      avoid: ["reservation"]     # optional: words not to use for this concept
  decisions:                     # every stakeholder decision from grilling
    - id: "D-3f2a"               # random 4-hex, unique within the Product
      decision: "Holds expire after 15 minutes."
      decided_by: "Jane Doe"
      decided_at: "2026-11-22"
      # three-gate decisions add:
      alternatives: ["No expiry", "24 hours"]
      rationale: "Inventory is scarce on weekends."
      resolves: "Q-91c0"         # optional: the open question this answered
  open_questions:                # unresolved items; keeps the record honest
    - id: "Q-91c0"               # random 4-hex, unique within the Product
      question: "Which payment provider holds funds?"
      needs: "tech-lead"         # tech-lead | stakeholder
      relates_to: ["INT-7c21"]   # optional: Intentions/Expectations it affects; empty = whole Product
```

**IDs.** Decision and question IDs are a type letter plus four random hex
characters (`D-xxxx`, `Q-xxxx`), checked unique within the Product, following the
hash convention so concurrent branches don't collide.

**Open-question lifecycle.** When a question is answered, it is removed from
`open_questions` and recorded in `decisions` with `resolves: <Q-id>`. The brief
shows only open questions and decisions; history lives in Git.

**Who writes the Product.** Interview, the PM-path authoring modes, quick-spec,
write-spec and an approved retro may append glossary terms, decisions and open
questions. Appends ride the stage's existing save confirmation but are listed
explicitly as Product changes in the batch summary. The stage keeps the Product's
original bytes as its baseline; if the Product changed since then, it stops and
re-reads rather than overwriting.

Intentions and Expectations do not get their own glossary; they inherit the
Product's. Decisions and open questions raised during outcome authoring are
appended to the Product (Claude's call: one decision log per Product keeps the
brief single-sourced). Specs inherit the glossary through the existing context
inheritance. An open question is relevant to a Spec when its `relates_to`
includes one of the Spec's Expectations or their Intention, or when `relates_to`
is empty. write-spec must resolve each relevant question (recording a decision)
or stop; gap-check reports an unresolved relevant question as a blocking finding,
so the Spec cannot be executed until a tech lead or stakeholder answers it.

### 1.4 Handoff brief

- Path: `docs/products/<Product YAML stem>.md`, for example
  `docs/products/PROD-f67b-idd-framework.md`.
- Content, rendered from YAML only: problem, audience, value, owner; glossary;
  decisions (full entries for three-gate ones); each Intention with its
  Expectations, validation and confirmed edge cases; inherited technical context;
  open questions grouped by `needs`.
- Header states that it is generated, names the source files and render date,
  and says to correct it in chat, not by editing.
- **Re-running on an existing Product** grills only gaps: required or optional
  fields that are missing or empty, an empty glossary, open questions, Expectations
  with fewer than two confirmed edge cases, and claims that contradict the repo.
  Confirmed fields are not re-asked unless contradicted. Changes use the normal
  confirmation gate.
- Rendered by the agent from a brief template reference
  (`plugin/references/authoring/brief-template.md`) after every successful save in
  interview and the PM-path authoring modes. No Node or other runtime in
  consuming projects.
- Validation (`npm run check`) must accept `.md` files beside Product YAML.
- Optional Claude adapter step: when a document/artifact publishing tool is
  available, offer to publish the brief. Codex adapter: same, if Codex Pages
  supports it (unverified). The core workflow never depends on either.

### 1.5 Model tiers

`product-interviewer`, `intention-author` and `expectation-author` move from
haiku to sonnet. Update CLAUDE.md's model table and any inventory/model
fixtures `npm run check` compares against.

## Design — Part 2: retro stage

### 2.1 Placement

`gap-check → implement-spec → review-spec → retro → archive`

New stage `retro`: canonical workflow `plugin/workflows/retro.md`, Claude
command `plugin/commands/retro.md`, a standalone bundle and a router stage
entry. Input: one Spec ID. Runs in the main conversation; no new agent (Claude's call:
analysis is reading a handful of reports, and keeping it in the main conversation
keeps approvals and writes there). Model policy follows the host.

### 2.2 Evidence

Read, in order, and cite every candidate to a file and section:

1. Execution reports for the Spec (`spec_gaps_encountered`, deviations).
2. Gap-check reports (findings, and gaps later found that it missed).
3. The review-spec validation report (failures, unverified items, human checks).
4. Guildhall quest plans under `docs/guildhall/plans/` that name the Spec:
   Not yet specified, Decisions, Lessons, reviewer findings.
5. Optionally, a host session log the user points to.

A candidate that cannot be traced to evidence is dropped.

### 2.3 Where findings go

Fixes split by who can apply them. Installed plugin files are read-only in a
consuming project, so framework-level improvements become upstream feedback.

| What went wrong | Fix lands in | Applied by |
|---|---|---|
| Spec lacked a fact the implementer needed | Product context, glossary or decisions | Main conversation, after approval |
| Vocabulary confusion | Product glossary | Main conversation |
| Judgement-call mistake the reviewer missed | Product `context.conventions` (inherited by Specs, read in review) | Main conversation |
| Mechanical mistake (pattern, banned API, file location) | Automated check in the project | Follow-on Spec (draft with Context and Expectation proposed) |
| Agent struggled to find files or facts | Navigation pointer in a file it already reads, or Product context code references | Main conversation |
| Gap-check should have caught it | Gap-checker attack list | Upstream feedback in the report |
| Template or checklist gap | IDD template / completeness checklist | Upstream feedback in the report |
| Process friction (WIP, hand-offs) | Logged for the periodic process retro | Report only |

### 2.4 Flow

1. Select the Spec; gather evidence read-only.
2. Present candidates ranked by severity, each with evidence, proposed fix,
   destination and who applies it.
3. The human approves, edits or rejects each candidate.
4. Apply approved local fixes with the same safe-YAML and confirmation rules as
   authoring; re-render the Product brief if Product YAML changed. Draft
   follow-on Specs only for approved mechanical checks.
5. Write `docs/reviews/SPEC-<id>-retro.md` with frontmatter `spec: SPEC-<id>`,
   `date` and `lessons` (one to three strings), then the candidates, decisions,
   applied changes and upstream feedback. A second retro for the same Spec uses
   `SPEC-<id>-retro-<YYYYMMDD>.md`.

No candidate means a short report saying so; that is a valid outcome.

### 2.5 Nudges and ledger

- review-spec's closing message suggests running retro when the Spec has any
  `spec_gaps_encountered`, gap-check findings or review failures.
- archive classification warns (does not block) when a Spec with non-empty
  `spec_gaps_encountered` has no review file whose frontmatter `spec` names it.
- Ledger records gain an optional `lessons` field copied from the retro
  frontmatter (all retros for the Spec, newest first, capped at three lines);
  retro reports are co-archived under `links.reports`.
